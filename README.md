# WooCommerce Starter Repo

## Опис

Це стартовий репозиторій для розробки сайту на WordPress + WooCommerce.

В основі використовується Bedrock — більш зручна та сучасна структура WordPress-проєкту, де залежності керуються через Composer, а код і конфігурація організовані акуратніше, ніж у стандартній збірці WordPress.

## Для чого цей репозиторій

Цей репозиторій потрібен як готова база для запуску інтернет-магазину. Його можна використовувати для:

- створення магазину на WooCommerce;
- додавання товарів, категорій та атрибутів;
- налаштування кошика, checkout і оформлення замовлень;
- підключення оплат, доставки та інших інтеграцій;
- подальшої кастомної розробки теми та функціоналу.

## Що вже є в проєкті

- WordPress як CMS;
- WooCommerce як основа магазину;
- Bedrock для зручної структури проєкту;
- підтримка Composer для керування залежностями;
- тема на базі Sage для подальшої кастомізації фронтенду.

## Структура проєкту

- [web](web) — публічна частина сайту;
- [web/app](web/app) — теми, плагіни, mu-плагіни, uploads;
- [web/wp](web/wp) — ядро WordPress;
- [config](config) — конфігурація середовищ;
- [composer.json](composer.json) — PHP-залежності проєкту.

## Локальний запуск

Зазвичай робота з проєктом відбувається так:

1. встановити залежності через Composer;
2. налаштувати файл середовища з локальними змінними;
3. підняти локальну базу даних;
4. запустити сайт у локальному середовищі.

### Git-хуки

У корені є `package.json` лише під husky — тема має власний у
`web/app/themes/sage`. Після клонування:

```bash
bun install   # або npm install -- ставить husky і прописує core.hooksPath
```

`.husky/pre-commit` проганяє `vendor/bin/pint` через lint-staged тільки по тих
`.php`, що йдуть у коміт: що pint переформатував, те lint-staged сам додає назад
до індексу, а непарсабельний файл валить коміт. У CI крок `lint` — це
`pint --test` по всьому дереву, тож хук тримає його зеленим.

Якщо pint ще не встановлений (`composer install --no-dev`), хук пропускає
перевірку з попередженням. Разовий обхід — `git commit --no-verify`.

## Коротко

Якщо простими словами: це не просто чистий WordPress, а вже підготовлена стартова база саме під WooCommerce сайт, яку можна брати за основу для магазину й далі розвивати під потрібний дизайн та бізнес-логіку.

## Розгортання

Перевірки й деплой живуть в одному конвеєрі — `.woodpecker/ci.yaml`. Деплой у
`dev` іде на пуш у гілку `dev`; прод-кроки поки закоментовані.

Конвеєр ставить composer-залежності, ганяє pint і pest, збирає тему, **окремо
збирає editor-assets плагіна `frontenda-blocks`** (він тримає
`blocks/section/build/` у `.gitignore`, тож composer-архів приходить без
зібраного JS), розкладає все через `rsync --delete`, скидає кеш Acorn, чистить
кеш LiteSpeed і гасить кеш Hostinger через їхній API.

### Секрети Woodpecker

| секрет | для чого |
| --- | --- |
| `ssh_host`, `ssh_port`, `ssh_user`, `ssh_private_key` | доступ для `rsync` і `ssh` |
| `deploy_path` | коренева тека сайту на сервері |
| `hostinger_account` | username хостинг-акаунта для Hostinger API |
| `hostinger_api_token` | токен Hostinger API |

Крок `validate-secrets` перевіряє їх усі ще до збірки, щоб конвеєр не падав на
півдорозі — і щоб `rsync --delete` ніколи не поїхав з порожнім `deploy_path`.
Він ловить тільки **порожні значення**; відсутній секрет до кроку взагалі не
доходить (див. нижче).

**Опційних секретів у Woodpecker немає.** `from_secret`, що вказує на
неіснуючий секрет, валить увесь конфіг з `secret "<name>" not found` ще до
того, як стартує перший крок, — жодна перевірка всередині кроку цьому запобігти
не може. Тому кожне ім'я з таблиці має реально існувати, і для кожної події, на
якій ці кроки працюють.

Звідси дві пастки, якщо колись додаватимеш нові секрети:

- **імена точно в нижньому регістрі.** У Woodpecker 3.x імена секретів
  регістрозалежні, він більше не приводить їх до верхнього автоматично;
- **у подіях має бути і `push`, і `manual`** — у деплой-кроків є
  `event: manual`, а новий секрет за замовчуванням доступний лише для `push`,
  `tag` і `deployment`, тож ручний деплой упаде з тією ж `secret not found`.
  Найпростіше продублювати набір подій із наявних `ssh_*`. `pull_request` не
  вмикати: токен не має світити у форкові PR.

### Домен за гілкою

Жоден крок не хардкодить домен — він виводиться з `CI_COMMIT_BRANCH`:

| гілка | домен |
| --- | --- |
| `dev` | `dev.kwiaty-bukiety.com.pl` |
| `main` | `kwiaty-bukiety.com.pl` |

Невідома гілка — крок падає з явним повідомленням, а не чистить кеш чужого
домену. Звідси ж беруть домен і smoke-тест, і виклик Hostinger API, тож коли
прод-кроки розкоментують, нічого доправляти не треба.

### Кеш Hostinger

Кеш Hostinger стоїть **перед PHP**, тож `wp litespeed-purge` його не дістає;
там, де ввімкнений Hostinger CDN, цей же виклик гасить і edge. Якщо його не
скинути, у кеші лишається HTML, який посилається на хешовані імена ассетів
попередньої збірки — а `rsync --delete` їх щойно видалив.

```
DELETE https://developers.hostinger.com/api/hosting/v1/accounts/{username}/websites/{domain}/cache/clear
```

Три моменти:

- крок іде **після** `maintenance-off`, і це не випадково: якщо чистити кеш,
  поки ще віддається 503, кеш перезаповниться сторінкою maintenance і буде
  віддавати її весь TTL — тобто рівно та аварія, яку цей крок має не допускати;
- запит, який пішов і не вдався, **валить крок**, і це навмисно: зелений деплой
  зі стейловим кешем — саме той баг, проти якого крок стоїть;
- опційний параметр `?directory=` націлює на WordPress у підпапці. Ми його не
  передаємо — без нього чиститься весь сайт, що нам і треба. Варто пам'ятати,
  якщо колись здасться, що чистка не зачепила `web/wp`.

Усі workflow у `.github/workflows/` лишаються в репо, але **жоден не
запускається сам** — у кожного тільки `workflow_dispatch`. Push-роботу тримає
Woodpecker, а GitHub Actions лишився ручним запасним варіантом.

### Чому один файл, а не два

Раніше було два конвеєри — `test.yaml` і `deploy.yaml` із `depends_on: test`.
Woodpecker дає кожному конвеєру власний workspace, тож на кожен пуш у `dev`
`composer install` і `bun install` для sage робилися **двічі**. В одному файлі
вони робляться раз, кроки діляться кешем у `/woodpecker/cache`, а деплой
відрізаний по `when`, а не по залежності між файлами.

Що ще змінилося для швидкості:

- кроки мають `depends_on`, тож `lint`, `test` і збірка плагіна йдуть
  паралельно, а збірка теми стартує одразу, не чекаючи composer;
- окремого `typecheck` немає — `bun run build` це `tsc && vite build`, тобто
  збірка теми вже і є перевірка типів;
- конвеєр на `push` запускається тільки для `dev` і `main`. Фіча-гілка
  перевіряється через свій pull request, інакше кожен PR давав два прогони.

### Maintenance під час деплою

`rsync` не атомарний: посеред синхронізації на сервері можуть одночасно лежати
нові шаблони й старий автолоадер. Тому крок `maintenance-on` перед `rsync`
вмикає maintenance, і WordPress на весь час деплою віддає
`web/app/maintenance.php` — сторінку з кодом **503**, `Retry-After` і
`noindex`. `maintenance-off` знімає його після деплою.

Перемикає `wp-cli`:

```bash
wp maintenance-mode activate --force
wp maintenance-mode deactivate
```

Він бере `ABSPATH` із `wp-cli.yml` (`path: web/wp`), а не з хардкоду, і
`WP_Upgrader::maintenance_mode()` під ним пише той самий
`<?php $upgrading = <int>; ?>`, що й сирий фолбек.

Деталі, які легко зламати:

- **`--force` обов'язковий.** Без нього `activate` виходить з кодом 1 і текстом
  `Maintenance mode already activated`, якщо файл лишився від убитого прогону —
  і деплой падав би ще до старту. `--force` ще й освіжає timestamp;
- **`deactivate` теж виходить з 1**, якщо maintenance не активний, тому він
  обгорнутий у `|| true`, а справжню гарантію дає `rm -f` після нього;
- **обидві команди піднімають WordPress і лізуть у БД** (конструктор команди
  будує `WP_Upgrader`). Тому обидва кроки мають фолбек на сирий файл: wp-cli на
  сервері може не бути, а `maintenance-off` працює вже **після** `rsync` — саме
  в той момент, коли новий код або БД можуть бути зламані й wp-cli не
  забутстрапиться, щоб зняти прапорець;
- `.maintenance` виключений із `rsync` (`--exclude="/web/wp/.maintenance"`),
  інакше `--delete` знесе його посеред синхронізації;
- timestamp має бути **літеральним int**, а не `time()`. WordPress знімає
  maintenance сам через 10 хвилин, порівнюючи `time() - $upgrading` — з
  `time()` різниця завжди нульова і сайт лежав би, поки хтось не прийде руками;
- `maintenance-off` має `status: [success, failure]`, тож спрацьовує і на
  зламаному деплої: майже всі падіння — це авторизація чи мережа, коли жоден
  файл ще не поїхав, і тримати 503 десять хвилин просто так немає сенсу;
- `maintenance.php` виконується до плагінів і теми, тому в ньому не можна
  викликати функції WP і не можна тягнути зовнішні ресурси — лише чистий PHP,
  інлайновий CSS і жодного запиту.

### Версіювання

Версію підіймає `.github/workflows/versioning.yml` — **у PR, до мерджу**, а не
після. Запуск ручний: у Actions треба стартувати workflow і передати номер PR
(`pr_number`), бо без події `pull_request` йому нізвідки взяти гілку.
`bump-dev-version.mjs` читає коміти PR і рахує рівень за conventional
commits: `!:` або `BREAKING CHANGE:` → major, `feat:` → minor, `fix:` → patch,
решта не рахується. Новий номер пишеться в `composer.json` і `style.css` окремим
комітом `chore(release): bump dev version` у гілку PR.

Базова версія береться з `dev` через API, а не з гілки PR, тому повторні пуші в
той самий PR не нарощують номер — перерахунок завжди дає те саме число, і коміт
просто не створюється.

Чому до мерджу: мердж у `dev` це сам по собі пуш, і Woodpecker починає деплой
одразу. Бамп після мерджу додавав другий коміт, той тригерив другий конвеєр, і
перший встигав доставити версію без бампу — а два `rsync --delete` ішли в одну
теку. Тепер мердж-коміт уже несе потрібну версію і деплой один.

Пуш сам по собі версію **не** підіймає — ні прямий у `dev`, ні в гілку PR.
Бамп відбувається лише тоді, коли workflow запустили руками.

### Що треба на сервері окремо

- `.env` — не деплоїться (виключений із rsync і з git). Для `dev` став
  `WP_ENV=staging`, інакше або сайт індексується, або в публіку світять помилки.
- `.htaccess` — теж не деплоїться.
- Таблиця поштових індексів:

  ```bash
  wp acorn postal-codes:install
  wp postal-codes import data/postal-codes.csv
  ```

  Без неї автокомпліт міста й індексу в чекауті не працює.

### Перенести прод на локальну машину

```bash
mysqldump -h <host> -u <user> -p --single-transaction --default-character-set=utf8mb4 <database> > stage-$(date +%F-%H%M).sql
tar -czf uploads-$(date +%F-%H%M).tar.gz web/app/uploads
```

Локально:

```bash
mysql -h database -u wordpress -ppassword wordpress < stage-<timestamp>.sql
tar -xzf uploads-<timestamp>.tar.gz
wp search-replace 'https://dev.kwiaty-bukiety.com.pl' 'http://localhost:8084'
```

## Блоки

Секції сторінок будуються з `fa/section` — блока з плагіна
[frontenda-blocks](https://github.com/IvankoBoichuk/frontenda-blocks), який
ставиться через composer. Variant і layout секції обирають PHP-шаблон:
спершу шукається `web/app/themes/sage/frontenda-blocks/section/<variant>-<layout>.php`
у темі, і лише потім шаблон плагіна. Кожен такий файл — тонкий місток до
однойменного Blade у `resources/views/frontenda-blocks/section/`.

Після змін у плагіні:

```bash
composer update frontenda/frontenda-blocks
cd web/app/plugins/frontenda-blocks && bun install && bun run build
```
