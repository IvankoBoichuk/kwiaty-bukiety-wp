# Скріншоти на різних розширеннях

Робить full-page скріншот кожного шаблону — головна, товар, категорія товарів, стаття
блогу (ті самі сторінки, що й у [perf-гейті](../perf/targets.ts)) — на 16 найпоширеніших
розширеннях: 6 мобільних, 4 планшетні, 6 десктопних. Список і звідки він узявся —
у [viewports.ts](viewports.ts).

Крім картинки, кожен тест дивиться на дві речі, які на зменшеному скріншоті легко пропустити:

- **чи сторінка не ширша за екран** (горизонтальний скрол на телефоні) — тест називає
  елементи, що вилазять;
- **чи всі картинки завантажились** — биті позначаються в галереї жовтим як
  попередження, але тест не валять. Майже завжди це картинки, яких немає локально (див.
  «Потрібні локальні `uploads`» нижче). Тест один раз пробує довантажити биті.

Скріншот зберігається в будь-якому разі. Падає тест лише через скрол вбік.

## Галерея

Після кожного прогону всі знімки збираються в одну сторінку:

```bash
bun run screenshots:gallery            # відкриває .output/gallery.html
```

Групування за сторінкою (мобілка / планшет / десктоп окремими рядами) або за розширенням,
фільтр за типом пристрою, «тільки з проблемами», масштаб і вибір сайту, якщо знімали
кілька. Клік по знімку відкриває його на весь екран: ←/→ — сусідні, Пробіл — 1:1, Esc —
закрити. Прогін з фільтром (`--project`, `--grep`) оновлює лише свої знімки, решта
лишається в галереї з минулих прогонів (`.output/manifest.json`).

## Запуск

```bash
bun run screenshots                    # devcontainer, http://localhost:8000
bun run screenshots:report             # HTML-звіт з усіма картинками

SCREENSHOTS_BASE_URL=https://dev.kwiaty-bukiety.com.pl bun run screenshots

bun run screenshots -- --project 'mobile-*'          # лише мобільні
bun run screenshots -- --project tablet-768x1024     # одне розширення
bun run screenshots -- --grep Product                # одна сторінка
```

Devcontainer заливається з дампа dev-бази, тому для нього беруться шляхи `dev`
(`/produkt/…`, `/kategoria-produktu/…`, статті з датою). Якщо сайт не відповідає, прогін
одразу падає з однією помилкою, а не 64 червоними тестами.

Тести знімають те, що сайт віддає зараз, тобто **зібрані** асети з `public/build`. Після
змін у шаблонах чи CSS тему треба перезібрати: `bun run build` у `web/app/themes/sage`.

Перший раз потрібен браузер: `node node_modules/@playwright/test/cli.js install chromium`.

Картинки лягають у `.output/<сайт>/<сторінка>/<група>-<ширина>x<висота>.png`, напр.
`.output/localhost-8000/home/mobile-390x844.png`. Каталог у `.gitignore`; повний набір важить ≈ 130 МБ.

## Стабільна версія і порівняння

Позначаєш поточні знімки як стабільні, вносиш зміни, проганяєш тести ще раз — і галерея
показує, що змінилось.

```bash
bun run screenshots                    # знімки «до»
bun run screenshots:approve            # позначити їх стабільними
# ...зміни в темі, перезбірка...
bun run screenshots                    # знімки «після», порівняння зі стабільними
bun run screenshots:gallery            # «Показати: зміни»
```

Кожен знімок порівнюється зі своєю стабільною копією попіксельно (pixelmatch). Картка
показує «Змінено 2.31%» (і зміну висоти сторінки, якщо є) або «Без змін». У перегляді на
весь екран є режими **Нова / Стабільна / Накладання / Шторка / Різниця** (клавіші 1–5),
повзунок для прозорості чи шторки, і переглядач одразу прокручує до першої зміни.
Кнопка «Затвердити» копіює команду, що робить стабільним саме цей знімок.

Затверджувати можна не все одразу — фільтр шукає входження в `<сайт>/<сторінка>/<розширення>`:

```bash
bun run screenshots:approve -- home                              # одна сторінка
bun run screenshots:approve -- localhost-8000/home/mobile-390x844
bun run screenshots:approve -- --force                           # разом з битими/проваленими
```

Знімки з проваленим тестом або битими картинками без `--force` пропускаються: стабільна
копія з дірками показувала б їх «виправленими» на кожному наступному прогоні.

Стабільні копії лежать у `.output/stable/`, різниця — у `.output/diff/`; обидва в
`.gitignore`, тобто стабільна версія своя на кожній машині.

Що зроблено, щоб «змін» не було там, де нічого не мінялося:

- **годинник сторінки зафіксований** (`page.clock.setFixedTime`), тож таймер доставки в
  хедері завжди показує одне й те саме;
- **«Podobne produkty» замінені заглушкою фіксованої висоти**: WooCommerce перемішує схожі
  товари на кожному запиті, а назви різної довжини ще й змінюють висоту блоку.

**Потрібні локальні `uploads`.** Без них `.htaccess` у devcontainer перенаправляє кожну
картинку на dev, а той під повним прогоном частину не віддає, а частину віддає в іншому
варіанті (LiteSpeed) — і порівняння показує зміни там, де їх немає. Скачати:

```bash
rsync -az --info=progress2 -e "ssh -p 65002" \
  u958399693@82.25.102.95:/home/u958399693/domains/dev.kwiaty-bukiety.com.pl/public_html/web/app/uploads/ \
  web/app/uploads/
```

### Змінні оточення

| Змінна | За замовчуванням | Призначення |
| --- | --- | --- |
| `SCREENSHOTS_BASE_URL` | `http://localhost:8000` | Який сайт знімати |
| `SCREENSHOTS_ENV` | `dev` для devcontainer, інакше з хоста | Чиї шляхи брати з `tests/perf/targets.ts` |
| `SCREENSHOTS_DPR` | `1` | Щільність пікселів; `2` — retina-якість, файли вчетверо більші |

## Що варто знати

- **Cookie-банер CookieYes схований CSS-ом**, а не прийнятий: інакше він закривав би низ
  кожного мобільного знімка, а клік «прийняти» вмикав би аналітику на кожному прогоні.
- **Перед знімком сторінка прокручується донизу**, щоб підвантажились `loading="lazy"`
  зображення в сітках товарів.
- **Мобільні й планшетні розширення мають мобільний user-agent** і touch, тож
  `wp_is_mobile()` і WooCommerce йдуть мобільною гілкою. Рендер — завжди Chromium.
- **Fixed-елементи** (липкий хедер, нижня мобільна навігація) на full-page знімку
  з'являються там, де стояли у першому екрані, а не внизу сторінки. Це особливість
  full-page скріншотів у Chromium, не баг верстки.
