# Lighthouse perf gate

Прогоняє Lighthouse (mobile) по чотирьох шаблонах — головна, сторінка товару, сторінка
категорії товарів, стаття блогу — і порівнює результат із бейслайном, що лежить у git.
Якщо показник просів більше, ніж дозволено, тест падає й показує таблицю з дельтою.

Це не бюджет «LCP має бути < 2.5s». Це детектор **відхилення**: питання не «чи сайт
швидкий», а «чи мої зміни зробили його помітно гіршим, ніж було».

## Запуск

```bash
bun run perf                 # порівняти з бейслайном
bun run perf:update          # прийняти поточні числа як новий бейслайн
bun run perf:report          # відкрити HTML-звіт Playwright з вкладеними звітами Lighthouse
```

Скрипти викликають `node node_modules/@playwright/test/cli.js`, а не `playwright`
напряму, і це не стиль. `bun run playwright` виконує CLI рантаймом Bun, а Playwright
під Bun не працює: браузер стартує, але таб, який відкриває Lighthouse, ніколи не
малюється, і кожен прогін валиться з `NO_FCP`. Той самий код під node проходить.

Один прогін Lighthouse — приблизно хвилина, за замовчуванням їх 3 вимірюваних плюс
прогрівальні, тобто повний цикл ≈ 3–4 хвилини локально і ≈ 10 на задеплоєному сайті. Для швидкої перевірки:

```bash
PERF_RUNS=1 bun run perf                       # один прогін замість трьох
bun run perf -- --grep "Product"               # лише сторінка товару
```

### Змінні оточення

| Змінна | За замовчуванням | Призначення |
| --- | --- | --- |
| `PERF_BASE_URL` | `http://localhost:8084` | Який сайт міряти |
| `PERF_ENV` | виводиться з хоста | Який файл `baseline/<env>.json` використати |
| `PERF_RUNS` | `3` | Кількість вимірюваних прогонів на сторінку (медіана) |
| `PERF_WARMUP_RUNS` | `1` локально, `3` на задеплоєних | Прогони, результат яких відкидається |
| `PERF_CDP_PORT` | `9222` | Порт CDP, через який Lighthouse говорить із браузером |
| `PERF_UPDATE_BASELINE` | — | `1` → перезаписати бейслайн замість порівняння |
| `PERF_REPORT_ONLY` | — | `1` → показати таблицю, але не падати |
| `PERF_CHROME_LIB_PATH` | див. нижче | Шлях до системних бібліотек Chromium |

`PERF_ENV` виводиться з хоста: `localhost` → `local`, `dev.*` → `dev`, решта → `prod`.
Це навмисно: порівнювати віддалений сайт за LiteSpeed із PHP-FPM у Docker немає сенсу,
тому кожне оточення має власний бейслайн.

## Системні бібліотеки Chromium

На машинах без root Chromium із кешу Playwright падає на `libnspr4.so` / `libnss3.so` /
`libasound.so.2`. Витягти їх без sudo:

```bash
PREFIX="$HOME/.local/share/chrome-deps"
mkdir -p "$PREFIX/debs" && cd "$PREFIX/debs"
apt-get download libnspr4 libnss3 libasound2t64
for d in *.deb; do dpkg-deb -x "$d" "$PREFIX"; done
```

Цей шлях — дефолтний: `config.ts` сам підкладає його в `LD_LIBRARY_PATH`, якщо каталог
існує. Інший розклад — через `PERF_CHROME_LIB_PATH`. В CI-образі Playwright це no-op.

## Прогрів

Перед вимірюваними прогонами йде HTTP-запит і один **Lighthouse-прогін, результат якого
відкидається**. Обидва потрібні, і ось чому.

HTTP-запит гріє лише HTML: PHP opcache, транзієнти WooCommerce, а на задеплоєних сайтах —
сторінковий кеш LiteSpeed, який пайплайн деплою щойно скинув. Гріти через сторінку
Playwright не вийде: коли та сторінка закривається, у браузера не лишається відкритого
вікна, і таб, який потім відкриває Lighthouse, уже ніколи не малюється — прогін падає
з `NO_FCP`.

Але HTML — не вся сторінка. **Браузерні** завантаження — це те, що змушує LiteSpeed
згенерувати WebP-варіанти зображень і дійти до своєї оптимізованої розмітки, і за один
хіт воно туди не доходить. Заміряно на головній dev: послідовні завантаження дали
1688 КБ, 1688 КБ, 371 КБ, 191 КБ, 191 КБ, а DOM по дорозі впав із 839 елементів до 739.
Стаціонарний стан настає приблизно з четвертого завантаження — тому на задеплоєних
сайтах відкидається три прогони, а не один.

Локально такого шару немає, одного прогону достатньо, і дефолт для задеплоєних додавав би
хвилини на сторінку задарма. Розширення `networkQuietThresholdMs` у Lighthouse пробувалось
першим і не дало нічого: стаціонарний стан той самий і з вікном тишини 3 с, просто до
нього все одно треба ті завантаження.

Крок `perf` у CI платить цей прогрів щоразу, і так і задумано: деплой кількома кроками
раніше скидає кеші LiteSpeed і Hostinger, тож сайт, який він міряє, завжди холодний.

## Як працює поріг

Для кожної метрики дозволене відхилення — це максимум із трьох величин:

1. абсолютний поріг (`abs` у `config.ts`, наприклад 300 ms для LCP);
2. відносний поріг (`pct`, наприклад 20% від бейслайну);
3. **розкид самого бейслайну** — різниця між `max` і `min` по його прогонах.

Третій пункт і робить гейт придатним до життя. Локальний стек дає розліт LCP на секунди
між ідентичними прогонами, тож фіксований поріг або не стріляв би ніколи, або стріляв би
щоразу. Розкид, записаний у бейслайн, — єдина чесна оцінка того, скільки руху не означає
нічого. На dev, де LiteSpeed віддає ті самі байти, розкид стискається майже до нуля і
починають працювати налаштовані пороги.

### Що міряється

Оцінки категорій (0–100): Performance, Accessibility, Best practices, SEO. Для
Accessibility / Best practices / SEO допуск нульовий — вони детерміновані, будь-яке
просідання є регресією. Performance має допуск 5 пунктів, бо складається з таймінгів
нижче й успадковує весь їхній шум.

Таймінги: FCP, LCP, Speed Index, TBT, CLS, TTFB, JS bootup, main-thread work.

Вага сторінки: transfer size, unused JS, unused CSS, кількість DOM-елементів, кількість
запитів. Саме ця група й виправдовує прогін на шумній машині — вона майже не рухається
між прогонами, тому вузький поріг тут ловить реальні регресії (зайва бібліотека в Vite,
шаблон, що перестав лінивити картинки) задовго до того, як таймінги дійдуть згоди.

## Коли оновлювати бейслайн

`bun run perf:update` — усвідомлено, після того як подивився, **чому** числа змінилися.
Бейслайн лежить у git, тому діф по `baseline/<env>.json` у PR — це і є слід рішення
«ми приймаємо цю зміну продуктивності», і ревʼювер його бачить.

`--grep` працює і тут: оновиться лише та сторінка, що потрапила у прогін, решта
залишиться як була.

## Чому гейт локальний, а CI лише звітує

Крок `perf` у CI друкує таблицю і **не валить пайплайн**. Причина конкретна.

Задеплоєний сайт не віддає стабільний документ. Заміряно на dev: усі чотири сторінки
перекидаються між важким варіантом і обрізаним, у якому зображення не завантажуються
взагалі — 144 КБ проти 1685 КБ на головній, 737 КБ проти 67 КБ на статті — і
перекидаються **в обидві сторони** між прогонами з різницею в хвилини, тягнучи за собою
оцінки Best practices і SEO. Це хостинговий шар (оптимізація LiteSpeed, lazy-load, стан
edge-кешу) віддає дві різні сторінки, а не шум вимірювання: 67 КБ на сторінці WooCommerce
— це документ без картинок. Тому жодне число, зняте там, не спільномірне з наступним, і
прогрів тут не допомагає.

Варто подивитись у налаштуваннях LiteSpeed Cache у бік Guest Mode / Guest Optimization —
саме вона віддає першому відвідувачу обрізану сторінку, і це типове джерело рівно такої
картини.

Коли це розрулиться, крок стає гейтом: прибрати `PERF_REPORT_ONLY` з
`.woodpecker/ci.yaml`, більше нічого не треба. Доти справжній гейт — `bun run perf`
локально, де числа стоять на місці.

## Локальні застереження

- **query-monitor** активний на локалці й додає помітний оверхед. Бейслайн зняти з тим
  самим набором плагінів, що й порівняння, інакше числа не спільномірні.
- Прогони послідовні, один воркер. Паралельний Lighthouse міряє конкуренцію за CPU, а не
  сайт, тому `workers: 1` у конфізі — не оптимізація, а умова коректності.
- Playwright-ретраїв немає навмисно (`retries: 0`): ретрай перф-гейту перекидає кубик,
  поки шум не випаде вигідним. А от прогін, який **упав з помилкою** (`NO_FCP` від
  задеплоєного сайту за edge-кешем), повторюється один раз — він не дав результату
  взагалі, тож брати це за вердикт щодо коду немає сенсу. Редірект не повторюється:
  це не флак, а неправильний шлях у `targets.ts`.
- На сторінці товару `transfer size` гуляє десятками кілобайт між прогонами — блок
  схожих товарів щоразу підтягує інші зображення. Розкид у бейслайні це проглитає, але
  саме на цій сторінці поріг по вазі виходить ширший, ніж на інших.

Що з цього випливає на практиці: з прогрівальним прогоном локальні числа стоять дуже
щільно — на головній `transfer size` рухається на 8 байт між прогонами, DOM на 0,
TBT на 7 ms, FCP на 135 ms. Тобто гейт ловить і вагу сторінки, і детерміновані оцінки,
і таймінги — усе, крім грубих стрибків TTFB, під які поріг спеціально широкий.

## Сторінки

Шляхи задані в `targets.ts` **окремо для кожного оточення** — permalink-и локального
Bedrock і задеплоєних сайтів не збігаються (`/product/` проти `/produkt/`,
`/product-category/` проти `/kategoria-produktu/`, стаття з датою в URL на dev). Якщо
шлях відповідає 404 або редіректом, прогін падає з цим статусом, а не з загадковим
просіданням оцінки.

Слаґи — це контент, не код. Видалений товар доведеться тут замінити; оточення без запису
в `targetsByEnv` — помилка, а не фолбек на чужі шляхи.
